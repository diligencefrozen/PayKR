# PayKR v0.4 — 데이터 품질 패치

## 적용 순서
- v0.1 기반에 v0.3까지 포함한 누적 패치. 기존 `src/config/merchants.js`(활성화 설정), 인증키, DB를 덮어쓰지 않는다. 이미 DB 모드를 활성화했다면 품질 검수 완료까지 운영 전환을 보류하고 작업 브랜치에서 검증한다.
- 실행 중인 수집 Job은 해당 커밋을 사용한다. 종료된 후 패치를 별도 브랜치에서 검토·병합한다. 기존 v0.3 SQL(202611290002)은 미적용 시에만 적용한다. v0.4 신규 SQL 마이그레이션은 없다. `supabase/diagnostics/merchant_quality_review.sql`은 조회 전용 진단이다.
- `initial`이 진행 중이면 기존 v1 매핑을 그대로 적용한다. v0.4 배포 자체가 품질 재수집을 시작하지 않는다. `auto` / `resume`도 기존 초기 수집을 이어간다.
- Supabase SQL Editor에서 `select id,value from public.paykr_sync_state where id in ('initial','delta','quality_v2');`로 `initial.complete=true`를 확인하고, 가맹점 CSV를 백업한다.
- 기존 초기 수집 완료 후 GitHub Actions > PayKR merchant sync > Run workflow > main > `quality`, `max_pages=10`으로 먼저 실행한다. `quality_v2` 독립 체크포인트가 생긴다. 통계와 DB를 확인한 뒤 `quality / 500`으로 계속하거나 기존 예약 실행에 맡긴다. 작업 중 `auto`와 `resume`은 `quality`를 계속한다. 진행 중에는 delta 수동 실행을 차단한다.
- 새 규칙으로 전국을 다시 읽으므로 API 요청과 실행 시간이 추가로 소요된다. DB는 기존 업소번호 기준 upsert만 수행하며 데이터 일괄 삭제/초기화가 없다. 재검증 중 공개 검색을 활성화하지 않는 것이 안전하다. 수집 종료 로그 `Quality scan complete` 이후 `delta`를 실행한다. 향후 delta는 v2 규칙을 사용한다. 초기 수집, 재검증, 변경 동기화는 동일 GitHub concurrency group으로 실행된다.

## 진단
CSV를 프로젝트 외부(예: 다운로드 폴더)에 저장하고 Node 22에서:
```
node scripts/merchants/audit.mjs "C:\\Users\\YOURNAME\\Downloads\\paykr_merchants_rows.csv" "merchant-audit.json"
```
보고서에는 기존 데이터의 재검토 사유, 브랜드별 수집량(0 포함), 중복 후보 및 업소번호가 포함된다. 보고서를 저장소에 커밋할 필요가 없다. UTF-8 CSV와 기존 Supabase 컬럼 형식을 가정한다. 중복은 동일 브랜드·정규화된 이름·주소에 대해 검출하며 30m 이내인지 추가 표시한다. 주소·좌표가 같다고 해서 동일 점포라고 단정하지 않는다.

첨부된 서울 일부 6,323건 기준: v2 규칙 재대조 통과 6,231건, 검토 92건, 동일 브랜드·이름·주소 후보 21그룹, ID 중복 0건. 이는 기존 DB 데이터의 재평가이며 실제 영업/결제 확인이나 신규 누락 매장 수 추정이 아니다. 기존 CSV에는 업종 코드 및 미선별 원본 상호가 없으므로 코드 대조·누락률은 확인할 수 없다.

## 새 규칙
- 별칭 보완: 씨유, 지에스25, 스타벅스커피코리아, 뚜레쥬르 등. 카탈로그 브랜드를 변경하거나 새로운 애플페이 지원을 단정하지 않는다.
- 상호 및 상세 업종을 우선 대조, 가장 긴 브랜드 이름 우선. 애매한 일반명 브랜드, 타 업종, 시설 입점점포는 검토 대상으로 보류. 기존 v1에 있던 광범위 상위 업종 매칭을 줄인다.
- `scripts/merchants/category-codes.json`은 공식 소분류 코드→명칭 사전 확장 지점이다. 현재 실제 코드 값이 확보되지 않아 빈 사전이며 상세 업종명으로 검사한다. 공단의 `/smallUpjongList` 및 원본 `indsSclsCd` 확인 후에만 값을 채운다. 가짜 코드 추정 금지. 동일 재검증 도중 사전/규칙을 바꾸면 안 된다(변경 시 새로운 품질 버전 및 체크포인트 필요).
- 신규 수집에서 보류한 후보는 DB에 넣지 않으며 사유별 집계를 로그에 남긴다. 기존 DB에 이미 있는 검토 후보는 자동 비활성화하지 않는다. 최종 재검증 후 최신 CSV를 다시 내려받아 진단하고, 운영자가 공공 원본 및 필요 시 실시간 카카오 장소 정보와 비교하여 확정된 ID만 비활성화하는 별도 작업을 수행한다. 카카오 결과는 영구 저장하지 않는다. 실제 애플페이 결제 여부는 별도 판단한다.
- 삭제 변경 코드 명세 미확인: C/U 이외는 집계하고 건너뛴다. 검색 누락·매핑 실패·중복 의심만으로 폐업 처리하지 않는다. 자동 폐업 처리 및 실제 업종코드 매핑은 미완료다.

## 테스트 / 제한
`node scripts/check.mjs` 전체 실행. v2 별칭, 상세 업종 우선, 시설 입점 오류, 모호한 명칭, 코드 사전 확장, CSV 진단, 중복 후보, 별도 재수집 체크포인트, 기존 데이터 유지 테스트 포함. 실제 API 재수집이나 Supabase 운영 DB 변경, GitHub push, 브라우저 통합 테스트는 이 패치 생성 과정에서 하지 않았다.
